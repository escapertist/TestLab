# Design

## Context

См. `proposal.md` — Why. Текущее состояние: [`services/material.py`](src/testlab/services/material.py) содержит один use case `create_from_pdf`, который валидирует файл, парсит PDF, вызывает модель, пишет файл и сохраняет материал вместе с тестом в одной транзакции. `MaterialService` зависит от `GigaChatClient`, роутер возвращает `MaterialCreateResponse` с вложенным тестом. `FileStorage` ([`infrastructure/storage.py`](src/testlab/infrastructure/storage.py)) умеет только `save`/`delete`, чтения файла нет. Доменного исключения для конфликта нет: маппинг в [`errors.py`](src/testlab/errors.py) знает `400/401/403/404/413/500/502`.

Ограничения: схема БД не меняется (миграций нет, `create_all`), `tests` уже допускает несколько строк на материал, `testlab.db` и файлы — локальные. Ответ карточки уже типизирован как `test: TestOut | None`, то есть API готов показывать материал без теста.

## Goals / Non-Goals

**Goals:**

- Загрузка отвечает быстро и не зависит от GigaChat; её ответ однозначно говорит «файл принят».
- Генерация — отдельный идемпотентный по материалу вызов, при сбое не оставляющий теста.
- Границы слоёв сохраняются: чтение файла и вызов модели — через `infrastructure`, бизнес-правила — в сервисе, HTTP-коды — в централизованном маппинге.

**Non-Goals:**

- Фоновая генерация (очередь, `202` + опрос статуса), статус `generating`.
- Перегенерация теста (`?force`), редактирование вопросов, публикация.
- CRUD тестов (`GET /tests`, `PATCH`, `publish`), который описан в `docs/API.md` как план.
- Хранение извлечённого текста в БД.

## Decisions

### 1. Два эндпоинта вместо одного

```text
POST /materials                    201 MaterialOut            файл + запись материала, БЕЗ теста
POST /materials/{id}/tests         201 TestOut                чтение файла -> текст -> LLM -> тест+вопросы
```

Роутер нового действия — отдельный модуль [`routers/test.py`](src/testlab/routers/test.py) с `prefix="/materials"`, тег `tests`. Альтернатива — дописать маршрут в `routers/material.py`; отклонено: там уже пять обработчиков материала, а будущий CRUD тестов (`GET /tests`, `publish`) логичнее держать рядом с генерацией.

### 2. Текст извлекается дважды

Загрузка извлекает текст только для проверки «файл читается и в нём есть текст» и выбрасывает результат; генерация извлекает текст заново из сохранённого файла. Альтернатива — сохранять текст в новую колонку `materials.text`: отклонена, потому что это изменение схемы без миграций, дублирование данных и риск рассинхронизации при замене файла. Парсинг `pypdf` для 10 МБ стоит миллисекунды против секунд у модели, поэтому повторный разбор дешевле. Если генерация станет узким местом, кэш текста добавляется отдельным изменением.

### 3. Генерация — отдельный сервис

Новый [`services/test.py`](src/testlab/services/test.py):

```python
class TestService:
    async def generate_for_material(
        self, teacher_id: str, material_id: str, title: str | None = None
    ) -> Test: ...
```

Порядок внутри use case:

```text
material = uow.materials.get_by_id_and_teacher(id, teacher_id)   -> NotFoundError (404)
existing = uow.tests.get_by_material(id)                         -> ConflictError (409)
content  = await storage.read(material.file_path)                -> NotFoundError (404)
text     = extract_text(content)                                 -> MaterialValidationError (400)
generated = await llm.generate_test(text, closed=5, open=2)      -> LLMError (502)
test + questions -> uow.tests.create_with_questions -> uow.commit
except  -> uow.rollback() -> PersistenceError (500)
```

Побочных эффектов нет, поэтому компенсация не нужна: единственный необратимый шаг — коммит. `MaterialService` теряет зависимость от модели и переименовывает use case в `upload_pdf(...) -> Material`; сборка вопросов (`_build_questions`) и расчёт `generation_params` переезжают в `TestService`.

Альтернатива — оставить генерацию в `MaterialService`: отклонено, иначе материал-агрегат продолжит владеть жизненным циклом теста, а будущий CRUD тестов упрётся в тот же класс.

### 4. Чтение файла — через хранилище

`FileStorage` дополняется методом `async def read(self, path: str) -> bytes`; `LocalFileStorage.read` читает файл в потоке и при отсутствии файла бросает `NotFoundError("Файл материала не найден")`. Тем самым сервис не знает `pathlib`, а скачивание (`get_material_file`) продолжает возвращать `Path` для `FileResponse`.

### 5. `409` через новый `ConflictError`

В [`errors.py`](src/testlab/errors.py) добавляется `ConflictError(DomainError)` и строка маппинга `ConflictError → 409`. Роутеры по-прежнему без `try/except`.

Почему `409`, а не `200` с существующим тестом: клиент обязан отличать «я только что создал» от «уже было», иначе кнопка будет молча показывать старый тест; по `docs/API.md` конфликты уже отдаются как `409`.

### 6. Контракт ответа загрузки

`POST /materials` возвращает `MaterialOut` (без `test`) и `201`. `MaterialCreateResponse` из [`schemas/material.py`](src/testlab/schemas/material.py) удаляется, `MaterialDetailOut` (с `test: TestOut | None`) остаётся для карточки. Время в ответе по-прежнему сериализуется `UtcDatetime` с `Z`.

### 7. Название теста

Тело запроса опционально: `{"title": "..."}` (1..255). Если поле не передано, название берётся из ответа модели (`GeneratedTest.title`), как сейчас. Это позволяет UI создать тест «одной кнопкой», не спрашивая имя.

### 8. Тесты

- API: загрузка (`201` без `test`, `400/401/403/413`), генерация (`201`, `409`, `404` на чужой материал и потерянный файл, `502`, `403`), карточка до и после генерации.
- Сервисы: `upload_pdf` не вызывает модель (фейк с `error` не должен ломать загрузку); `TestService` — успех, `ConflictError`, `NotFoundError`, компенсация при сбое коммита.
- Заглушка извлечения текста в API-тестах генерации переезжает на `testlab.services.test.extract_text`.

## Risks / Trade-offs

- [Ответ `POST /materials` меняется — ломается тот, кто читал `test` из загрузки] → единственный потребитель сейчас Swagger/ручные прогоны; `docs/API.md` обновляется, поле берётся из карточки.
- [PDF парсится дважды] → микросекунды против секунд модели; при необходимости кэшируется колонкой `materials.text` отдельным изменением.
- [Проверка «тест уже есть» не атомарна: два одновременных запроса могут создать два теста] → `409` защищает от повторного клика, но не от гонки; жёсткая защита потребовала бы `UNIQUE(tests.material_id)`, что запретило бы несколько тестов на материал в будущем. Принято как известное ограничение.
- [Генерация синхронная: 60 с таймаут модели держит HTTP-соединение] → это осознанный компромисс этапа; фоновая очередь — отдельное изменение со статусом `generating`.
- [Материал без теста теперь нормальное состояние] → интерфейс обязан отличать «нет теста» от «ошибки»; API отдаёт `test: null`, а `502` приходит только от действия генерации.

## Migration Plan

1. Добавить `read` в хранилище и `ConflictError` в маппинг — обратно совместимо.
2. Переписать `MaterialService.upload_pdf` и роутер загрузки, удалить `MaterialCreateResponse`.
3. Добавить `TestService`, `dependencies/test.py`, `routers/test.py`, зарегистрировать роутер в `create_app()`.
4. Обновить тесты и `docs/API.md`, прогнать `pytest` и `ruff`.
5. Ручной прогон: загрузка → карточка (`test: null`) → создание теста → карточка с тестом → повторное создание (`409`).

Схема БД не меняется, данные не мигрируют; откат — revert коммита. Материалы, загруженные до изменения, уже имеют тест, поэтому на них генерация ответит `409` — это ожидаемо.
